|层级|包含的库|在博客里管什么|
|---|---|---|

## 一次请求里，这些库怎么接力

以「访问一篇带代码的文章」为例，完整链路如下（按顺序对应到库）：

1. 浏览器发请求 → **waitress** 接住（生产模式）

2. **Werkzeug**（Flask 底层）解析请求，**Flask** 按路由找到 `post_detail` 函数

3. **Flask\-SQLAlchemy** 从 **SQLite**（blog.db）查出文章与评论

4. 正文 Markdown 没有缓存 → **python\-markdown** 转 HTML，**Pygments** 给代码块上色

5. **Jinja2** 把数据填进模板（**Tailwind CSS** 提供样式）渲染成最终网页

6. Flask 返回网页；桌面版场景下 **pywebview** 窗口负责显示，**PyInstaller** 打包的 exe 负责承载这一切

两个「隐形势力」也要认识：**YAML（PyYAML）** 负责文章头部信息和批量导入；**python\-dateutil** 只在导入自定义日期时出场。它们不常在主线，但缺了导入功能就废。

# 第一层 · Web 框架（Flask / Jinja2 / Werkzeug）

## Flask：博客的 Web 骨架

### 角色定位

所有网址路由、请求读取、页面渲染、接口返回都由它驱动。核心文件 `app.py` 的全部路由都是 `@app.route` 登记的。它是你以后改博客 90% 动作的主战场——加一个页面、改一个接口，本质都是「写一个 Flask 路由函数」。

### 原理大白话

**Flask 解决什么问题？**浏览器访问 `http://127.0.0.1:5000/post/3/` 时，服务器收到一个 HTTP 请求。如果不用框架，你要自己解析请求文本、自己判断「这个网址该干什么」、自己拼 HTML 字符串返回——极其痛苦。Flask 替你做了三件事：

1. **路由匹配**：用 `@app.route('/post/<int:post_id>/')` 这种「装饰器」把「网址长什么样」和「该调用哪个函数」绑定起来。请求一到，Flask 自动按规则找函数。
2. **请求封装**：把「网址参数、表单数据、请求头、客户端 IP」全部装进 `request` 对象，你直接读属性就行，不用自己解析。
3. **响应生成**：你返回字符串/模板/JSON，Flask 自动包装成标准的 HTTP 响应（带正确的状态码和 Content-Type）。

**为什么叫「微框架」？**核心只做上面三件事，数据库、登录、表单校验都不内置，要用时自己装扩展（项目就装了 Flask\-SQLAlchemy 管数据库）。好处是轻、灵活、学起来快；代价是「全家桶」功能要自己拼。

**Flask 和 WSGI 什么关系？**Flask 是一个 WSGI 应用——它不直接监听端口、不直接收网络字节流，而是「等别人把请求解析好递给它」。这个「别人」就是 WSGI 服务器：开发时是 Flask 自带的开发服务器，生产时是 waitress（第四层会讲）。正因为遵守 WSGI 约定，两者才能无缝切换。**一句话：WSGI 是 Flask 和服务器之间的「接口标准」，Flask 是「业务处理者」。**

### 核心 API 详解

|API|签名要点|项目中的用途|
|---|---|---|
|`Flask(__name__, template_folder=, static_folder=)`|第一个参数是模块名，用于定位资源；后两个指定模板/静态目录|app.py 第 122 行：目录用 `Config.RESOURCE_DIR` 拼接，保证打包后也能找到资源|
|`@app.route(rule, methods=[...])`|`rule` 支持动态参数 `<int:xxx>`；`methods` 限制请求方法|首页 `/`、文章详情 `/post/<int:post_id>/`、点赞接口 `methods=['POST']`|
|`request.args.get(name, default, type)`|读网址问号参数；`type` 参数做类型转换（如 `type=int`）|首页 `request.args.get('page', 1, type=int)` 读页码|
|`request.form.get(name)`|读表单 POST 字段|发文章表单的标题、正文、标签|
|`request.headers.get(name)`|读请求头|点赞指纹的一部分（User-Agent）|
|`request.get_json()`|读 AJAX 的 JSON 请求体|新手向导 4 个 JSON API|
|`render_template(name, **kw)`|渲染模板并返回；所有模板要用的变量都要传|每个页面路由的结尾|
|`redirect(url_for('函数名'))`|302 跳转；`url_for` 按路由函数名反推网址|保存文章后跳回列表|
|`flash(msg, category)`|存一条一次性提示（配合模板里 `get_flashed_messages`）|保存/删除成功提示|
|`jsonify(dict)`|返回 JSON 响应（状态码 200 + `application/json`）|点赞接口、同步 API|
|`abort(404)` / `@app.errorhandler(404)`|中断请求返回 404 / 自定义错误页|文章不存在时 `get_or_404` 内部用它|
|`@app.context_processor`|注册「全局模板变量注入器」，返回的 dict 每个模板都能用|`inject_globals()`（第 843 行）：站点名、导航、分类等全站变量|
|`@app.template_filter('名字')`|注册自定义模板过滤器，模板里 `{{ 值 | 过滤器 }}` 调用|`_tpl_strftime`（第 814 行）格式化日期、`_tpl_localtime`（第 802 行）转本地时区|
|`app.config.from_object(Config)`|把配置类的类属性全部读进 `app.config`|第 125 行：端口、数据库 URI、上传限制等都从 config.py 来|

### 项目落地代码（真实源码）

**应用创建（app.py 第 122~124 行）：**

```python
app = Flask(__name__,
            template_folder=os.path.join(Config.RESOURCE_DIR, 'templates'),
            static_folder=os.path.join(Config.RESOURCE_DIR, 'static'))
app.config.from_object(Config)
```

**逐行解释：**① `__name__` 是 Python 的「当前模块名」，Flask 靠它定位资源，固定写法；② `Config.RESOURCE_DIR` 是项目自己定义的「资源根目录」——源码运行时指向项目目录，打包后指向 PyInstaller 的 `_internal` 目录（第六层详解），这样模板和静态文件两种环境下都能找到；③ `from_object(Config)` 把 config.py 里 Config 类的所有大写属性读进 `app.config`，之后代码里用 `app.config['POSTS_PER_PAGE']` 就能取到配置。

**一个完整路由（文章详情，第 1058 行）：**

```python
@app.route('/post/<int:post_id>/')
def post_detail(post_id):
    post = Post.query.get_or_404(post_id)
    ...
    return render_template('post_detail.html', post=post, comments=comments)
```

**三个要点：**① `<int:post_id>` 是动态参数——`/post/3/`、`/post/99/` 都进这个函数，`3`、`99` 会被转成整数传给 `post_id`；② `get_or_404` 查不到自动 404（不用自己写 if）；③ `render_template` 第一个参数是模板名，后面是「模板里要用的变量」。

**全局变量注入（第 843 行，性能优化版）：**

```python
@app.context_processor
def inject_globals():
    ...  # 静态路径直接短路，动态路径查 5 秒 TTL 缓存
    return {'site_name': '个人博客', 'profile': profile, 'tags': tags, ...}
```

**为什么需要它？**导航栏、站点名、分类列表这些「每个页面都有」的数据，如果每个路由都手动查一遍再传模板，会写 30 遍重复代码。`context_processor` 让这些变量**自动**出现在所有模板里。项目还做了性能优化：静态资源请求（CSS/JS/图片）完全不查数据库直接短路，普通页面 5 秒内复用同一份缓存——这是 v2.8.3 针对「一次页面加载触发 120 条 SQL」的优化。

### 高频坑详解

- **两个函数共用一个路由名** → `AssertionError: View function mapping is overwriting...`。Flask 默认用函数名当路由别名，重名会覆盖。**解法**：换函数名，或 `@app.route(..., endpoint='别的名字')` 显式起别名。

- **表单页只写了 `methods=['POST']`** → 直接打开页面 405。**解法**：新建/编辑页是「GET 显示表单 + POST 提交数据」两个动作，必须写 `methods=['GET', 'POST']`；纯操作类路由（删除、点赞）才只写 POST。

- **`request.form` 取不到值** → 十有八九是 HTML 里 `name="xxx"` 和代码 `request.form.get('xxx')` 名字对不上。**排查**：右键页面看源码，核对 name 属性。

- **生产环境开 debug** → 出错页泄露堆栈和源码，且 debug 模式带调试器可能被远程执行代码。**解法**：正式运行走 waitress，`debug` 永远 False。

- **SECRET_KEY 缺失** → session/flash 全崩（报 `RuntimeError: The session is unavailable` 或提示需设置 secret_key）。**解法**：项目在 config.py 里自动生成并持久化 SECRET_KEY，重启不丢。

- **模板变量没传** → Jinja2 把未定义变量渲染成空字符串，页面不报错但内容消失。**排查**：用 `{{ 变量 | default('缺失') }}` 快速定位。

## Jinja2：模板引擎

### 角色定位

把「HTML 骨架 + 数据」拼成网页。`{{ }}` 输出值，`{% %}` 写逻辑。所有 templates/ 页面都靠它。**理解 Jinja2 的关键一句话：模板是「带洞的 HTML」，洞由路由函数传进来的数据填上。**

### 原理大白话

**Jinja2 解决什么问题？**页面 90% 是重复的：每个文章卡片都长一样，只是标题/日期/链接不同。如果每个页面手写 HTML，改个导航栏要改 30 个文件。Jinja2 的方案是**模板继承 + 循环 + 条件**：

1. **继承**：`base.html` 定义全站骨架（导航、页脚、CSS 引入），用 `{% block %}` 开「插槽」；子页面 `{% extends "base.html" %}` 只填自己的插槽。改导航 = 只改 base.html 一个文件。
2. **循环**：`{% for post in posts %}` 把一篇文章的 HTML 模板重复渲染 N 遍——数据库返回多少篇，页面就生成多少个卡片。
3. **条件**：`{% if post.published %}` 按数据决定显示什么。
4. **自动转义**：`{{ post.title }}` 输出的内容中，`<`、`>`、`&` 等字符会被自动转义成安全实体——**这是防 XSS（跨站脚本攻击）的第一道防线**。只有你确认内容是可信 HTML 时，才用 `|safe` 关掉转义。

**模板渲染流程：**路由函数 `render_template('index.html', posts=posts)` → Jinja2 加载模板文件 → 解析 `{% %}` 和 `{{ }}` → 用传入数据替换 → 输出纯 HTML 字符串 → Flask 返回给浏览器。**注意：Jinja2 渲染发生在服务器端**，浏览器拿到的是最终 HTML，看不到模板语法。

### 核心语法详解

|语法|用途|项目例子|
|---|---|---|
|`{{ 变量 }}`|输出值，默认自动转义|`{{ post.title }}` 文章标题|
|`{{ 变量 | safe }}`|输出原始 HTML（不转义）|`{{ post.rendered_html | safe }}` 文章正文——这是 Markdown 渲染好的 HTML，必须 safe 否则显示成源码|
|`{{ 变量 | 过滤器(参数) }}`|管道语法：值经过函数加工再输出|`{{ post.created_at | strftime('%Y-%m-%d') }}` 格式化日期；`{{ 值 | default('缺失') }}` 给默认值|
|`{% extends 'base.html' %}`|模板继承：子页声明「我是 base 的孩子」|每个前台页面第一行都是它|
|`{% block 名字 %}{% endblock %}`|定义/填充插槽|base.html 里 `{% block content %}`，子页填内容|
|`{% include 'xxx.html' %}`|把另一个模板原样嵌入|导航、页脚等公共片段|
|`{% for x in 列表 %}{% endfor %}`|循环渲染|首页文章卡片、标签云、评论列表|
|`{% if 条件 %}{% else %}{% endif %}`|条件分支|`{% if profile %}` 有资料才显示「关于我」区块|
|`{% for ... %}{% else %}{% endfor %}`|空列表时执行 else|草稿箱空时显示「没有草稿」|
|`url_for('函数名', 参数=值)`|按路由反推网址（模板里也能用）|`url_for('post_detail', post_id=post.id)` 生成 `/post/7/`|
|`get_flashed_messages()`|读取一次性提示|保存成功后的绿色提示条|

### 项目落地代码（真实源码）

**base.html 骨架（所有页面的母版）：**

```html
<!DOCTYPE html>
<html lang="zh-CN" class="{% if dark_mode %}dark{% endif %}">
<head>

</head>

  {% include 'nav.html' %}            {# 导航栏：所有页面共享 #}
  <main class="...">
    {% block content %}{% endblock %} {# 插槽：子页面填这里 #}
  </main>
  {% include 'footer.html' %}         {# 页脚 #}
</body>
</html>
```

**子页面填充（index.html 开头）：**

```html
{% extends 'base.html' %}
{% block content %}
  {% for post in pagination.items %}
  <article class="...">
    <h2><a href="{{ url_for('post_detail', post_id=post.id) }}">{{ post.title }}</a></h2>
    <p class="text-gray-500">
      {{ post.created_at | strftime('%Y-%m-%d') }} · {{ post.view_count }} 次浏览
    </p>
  </article>
  {% endfor %}
{% endblock %}
```

**v2.8.3 的时区过滤器（app.py 第 802 行）：**项目新增了三个自定义过滤器，解决「数据库存的是 UTC 时间，显示比北京时间慢 8 小时」的问题：

```python
@app.template_filter('localtime')
def _tpl_localtime(dt):
    """naive UTC datetime -> 本地时间（模板显示用，避免 8 小时时差）"""
    if dt is None: return dt
    if getattr(dt, 'tzinfo', None) is None:
        dt = dt.replace(tzinfo=datetime.timezone.utc)   # 先声明它是 UTC
    return dt.astimezone()                               # 再转本地时区

@app.template_filter('strftime')
def _tpl_strftime(dt, fmt):
    """Jinja 无内置 strftime 过滤器；本地化后按格式输出"""
    if dt is None: return ''
    return dt.strftime(fmt)
```

**为什么要自己写？**Jinja2 没有内置的 `strftime`（格式化日期）过滤器，且数据库存的 `created_at` 是「无时区标记的 UTC 时间」，直接显示会差 8 小时。这两个过滤器配合使用：先 `|localtime` 转成北京时间，再 `|strftime('%Y-%m-%d %H:%M')` 按格式输出。**这是 v2.8.3 修复「同步后时间异常」的核心补丁。**

### 高频坑详解

- **忘记 endfor/endif** → `TemplateSyntaxError: tag name expected`。**解法**：`{% for %}` 必须以 `{% endfor %}` 收尾，`{% if %}` 必须以 `{% endif %}` 收尾；缩进好看但不强制，**闭合标签才是语法**。

- **该加 `|safe` 没加** → HTML 变文字（用户看到 `&lt;h1&gt;` 而不是标题）。正文、CSS 常量这类「可信 HTML」都要 `|safe`。

- **用户输入加了 `|safe`** → **XSS 漏洞**！用户能往你的页面注入脚本。**铁律**：只有你自己生成的、或经过白名单过滤的内容才 safe；用户提交的评论、昵称永远不要 safe（评论模板里昵称、内容都是 `{{ }}` 直接输出，靠自动转义防护）。

- **变量缺失不报错** → 渲染成空。**排查**：模板里临时加 `|default('缺失')`，刷新看哪个变量是「缺失」——对照路由的 render_template 参数列表补传。

- **打包版模板改不动** → 打包后模板在 `_internal` 只读区，改源码目录无效。**解法**：改 `D:\blog_pkg\templates\` 下的源文件后重新打包。

- **`{% if 变量 %}` 判断失灵** → 空列表 `[]`、空字符串 `''`、`0`、`None` 在 Jinja2 里都是假值。判断「列表是否为空」建议用 `{% if not posts %}`，判断「是否指定了某字段」注意空字符串也是假。

## Werkzeug：Flask 的底层引擎

### 角色定位

Flask 的依赖，负责请求解析/路由匹配/调试器。项目直接调用它的只有一处：`secure_filename()`——上传文件名的安全消毒（防路径穿越）。**平时你几乎感觉不到它，但它是 Flask 能跑起来的地基。**

### 原理大白话

**Werkzeug 是什么？**「Werkzeug」是德语「工具」的意思。它是 Flask 的底层 WSGI 工具库——Flask 的路由匹配、请求解析、响应生成，底层都是 Werkzeug 在做。你可以把 Flask 想成「餐厅经理」（定菜谱、管流程），Werkzeug 是「后厨设备」（锅碗瓢盆）。**你装 Flask 时它自动装好，不用单独装，但它的 `secure_filename` 你必须会——这是上传功能的安全底线。**

**路径穿越漏洞是什么？**用户上传文件名如果是 `../../etc/passwd` 或 `..\..\evil.md`，直接拼路径保存就会把文件写到项目目录之外，攻击者可能覆盖你的系统文件。`secure_filename()` 把这类危险字符全部处理掉，只保留安全的 ASCII 字符。

### 核心 API 详解

- **`secure_filename(文件名)`**：把中文/空格/`..`/`/` 等危险字符处理成安全 ASCII 名。**注意：中文会被替换成下划线或空**——这是安全设计，不是 bug。保存上传文件前必用。

- **配合写法**：`save_name = 时间戳 + '_' + secure_filename(file.filename)`——时间戳防同名覆盖，secure_filename 防路径穿越，双保险。

- **`file.seek(0)`**：文件对象读过内容（如验证图片）后，指针到了文件末尾；写盘前必须倒回开头，否则保存的文件是 0 字节。**这是上传功能最常见的隐性 bug。**

### 项目落地代码（真实源码）

项目里 `secure_filename` 用在文章图片/头像上传（可搜索 `secure_filename` 定位）：

```python
from werkzeug.utils import secure_filename
...
filename = secure_filename(file.filename)      # 消毒：防路径穿越
save_name = f"{int(time.time())}_{filename}"   # 加时间戳防同名覆盖
file.save(os.path.join(Config.UPLOAD_FOLDER, save_name))
```

**三步缺一不可：**① `secure_filename` 把 `../../evil.md` 变成 `evil.md`（`..` 和斜杠全没了）；② 时间戳前缀保证两个用户传同名文件互不覆盖；③ `file.save(绝对路径)` 落盘。

### 高频坑详解

- **中文文件名被改成下划线** → 这是安全设计。**解法**：要保原名自己写规则（比如只过滤 `..` 和路径分隔符，保留中文），但**不建议**——保留中文会引入编码和路径兼容问题，加时间戳前缀已经能避免重名。

- **不消毒直接拼路径** → **路径穿越漏洞**（`../../evil.md`）。**铁律**：任何用户提供的文件名，落盘前必须过 `secure_filename`。

- **保存后文件 0 字节** → 读文件内容后忘了 `file.seek(0)`。**解法**：`file.stream.seek(0)` 后再 `file.save(...)`。

- **打包后上传报错** → 上传目录写死了相对路径。**解法**：上传目录要用 `Config.UPLOAD_FOLDER`（基于 DATA_DIR，打包后指向用户数据目录而非 `_internal`）。

# 第二层 · 数据层（Flask\-SQLAlchemy / SQLite）

## Flask\-SQLAlchemy：数据库 ORM

### 角色定位

用 Python 代码操作数据库，管着 Post/Tag/Comment/Like/Profile/FriendLink 6 张表。增删改查、级联删除、分页、统计全是它。**它是你改博客第二高频的库——加字段、改查询、做统计都靠它。**

### 原理大白话

**ORM 是什么？**ORM（Object-Relational Mapping，对象关系映射）把「数据库的行」映射成「Python 对象」。没有 ORM 时你要写 SQL：`SELECT * FROM post WHERE id=3`；有 ORM 后你写 Python：`Post.query.get(3)`。**好处**：① 不用记 SQL 语法，用 Python 链式调用；② 数据库从 SQLite 换成 MySQL 代码不用改；③ 列名错误、类型错误在写代码时就能发现。

**Flask\-SQLAlchemy 和 SQLAlchemy 什么关系？**SQLAlchemy 是通用的 Python ORM 库（不依赖 Flask）；Flask\-SQLAlchemy 是它的 Flask 封装——把 `db` 对象和 Flask 应用绑定，让你在路由里直接用 `db.session` 操作，还自动处理「请求结束关闭连接」等琐事。**项目用的是 Flask\-SQLAlchemy 3.x 风格（`db = SQLAlchemy(app)`）。**

**查询链是怎么回事？**`Post.query.filter_by(...).order_by(...).limit(...).all()` 是「懒加载」——每个方法只返回一个「查询对象」，不真正执行 SQL；只有最后的 `.all()` / `.first()` / `.count()` 才真正访问数据库。**这让你能按条件逐步拼查询**（项目首页搜索就是这么做的：先过滤发布状态，有搜索词再加模糊条件，有分类再加分类条件，最后统一排序分页）。

**级联删除为什么必须配置？**删除文章时，它的评论怎么办？SQLAlchemy 默认行为是「把评论的 post_id 置为 NULL」——但评论表 post_id 是 NOT NULL（非空约束），于是报 `NOT NULL constraint failed: comment.post_id`。项目在 Comment 模型的 relationship 上配置了 `cascade='all, delete-orphan'`，删文章时**先自动删光它的评论**，再删文章本身。

**Post 模型（第 437 行，完整版）：**

```python
class Post(db.Model):
    """博客文章"""
    id = db.Column(db.Integer, primary_key=True)
    title = db.Column(db.String(200), nullable=False)
    summary = db.Column(db.String(500))              # 摘要（可选，自动生成）
    content = db.Column(db.Text, nullable=False)     # Markdown 原文
    rendered_html = db.Column(db.Text)               # 渲染结果缓存（性能优化）
    is_deleted = db.Column(db.Boolean, default=False)  # 软删墓碑（云同步基石）
    created_at = db.Column(db.DateTime, default=datetime.datetime.utcnow)
    updated_at = db.Column(db.DateTime, default=datetime.datetime.utcnow,
                           onupdate=datetime.datetime.utcnow)
    published = db.Column(db.Boolean, default=True)
    view_count = db.Column(db.Integer, default=0)
    category = db.Column(db.String(50))
    tags = db.relationship('Tag', secondary=post_tags,
                           backref=db.backref('posts', lazy='dynamic'))
```

**为什么这么设计（每条都是经验）：**① `rendered_html` 缓存列——Markdown 渲染一次要几十毫秒，存起来详情页直接读，不用每次重渲染（v2.8.3 性能优化核心）；② `is_deleted` 软删——删除不打 `DELETE` 而是打标记，这样云同步才能把「删除」这个动作同步到其他机器；③ `onupdate` 让 `updated_at` 每次修改自动刷新；④ `tags` 多对多关系通过中间表 `post_tags` 关联。

**查询链（首页搜索，第 1014 行）：**

q = Post.query.filter_by(published=True, is_deleted=False)

**轻量迁移补列（init_db 第 2248 行）：**

```python
with app.app_context():
    db.create_all()
    # 自动为旧数据库补充新增列（无迁移框架时的轻量方案）
    from sqlalchemy import inspect, text
    insp = inspect(db.engine)
    cols = {c['name'] for c in insp.get_columns('post')}
    if 'is_deleted' not in cols:
        db.session.execute(text('ALTER TABLE post ADD COLUMN is_deleted BOOLEAN DEFAULT 0'))
        db.session.commit()
```

**为什么必须 ALTER 而不是删库重建？**你的 `blog.db` 里已有文章数据，删库重建全没了。ALTER TABLE 只加一列、不动旧数据；`inspect` 先查列是否存在，存在就跳过——脚本幂等，启动 100 次也安全。

### 高频坑详解

- **忘了 `commit()`** → 数据没保存，重启就丢。**铁律**：`add`/`delete` 之后必须 `db.session.commit()`。调试时多写一句 `print` 确认走到了 commit。

- **删文章报 `NOT NULL constraint failed: comment.post_id`** → 评论外键非空，删除顺序不对。**解法**：项目已用 `cascade='all, delete-orphan'` 修复；如果你自己加表，注意「先删子表（点赞/评论）→ 再删主表（文章）」。

- **报 `database is locked`** → SQLite 同时被多个连接写。**解法**：连接串配 `timeout=30`（写锁等待 30 秒）；避免同时开两个实例（项目单实例锁会拦）；关掉占用数据库的其他程序。

- **脚本里用 db 报 `Working outside of application context`** → 在后台脚本/线程里用 db 必须包 `with app.app_context():`。**原因**：db 依赖「当前应用上下文」，脚本入口没有这个上下文。项目同步线程、init_db 都包了。

- **模型加列后查询报 `no such column`** → `create_all()` 只建新表，**不改旧表**。**解法**：用 init_db 里的 ALTER 补列模式（见上）。

- **`.first()` 返回 None 导致 `xxx.id` 报错** → 查询结果可能为空。**解法**：`if xxx:` 判空再取属性，或直接用 `get_or_404`。

## SQLite：数据库本体

### 角色定位

所有数据的家：`blog.db` 单文件数据库，零配置。项目通过 SQLAlchemy 操作它。**它是博客的「记忆」——文章、评论、点赞、友链、资料全在这一个文件里。**

### 原理大白话

**SQLite 是什么？**一个「把整个数据库装进一个文件」的关系型数据库。不像 MySQL 要装服务器、开端口、管账号，SQLite 就是**一个 .db 文件**，Python 内置支持，读写全在文件层面完成。**好处**：零配置、单文件易备份、个人项目性能完全够；**代价**：同一时刻只有一个进程能写（所以有 `database is locked` 的坑），不适合高并发。

**项目数据存在哪？**`data/blog.db`（数据目录）。**备份 = 复制这一个文件**；删掉它重启会自动重建（init_db 会建表 + 插入示例数据）——这就是「纯净版」的原理：把 blog.db 删了，打包出来的就是不带个人数据的全新博客。

**连接串 `sqlite:///路径/blog.db` 是什么？**SQLAlchemy 统一用 URL 描述数据库：`sqlite:///` 是 SQLite 协议头，后面跟文件路径。项目通过环境变量 `DATABASE_URL` 可覆盖，不设就用默认路径。

### 关键配置详解

|配置|值|作用|
|---|---|---|
|`SQLALCHEMY_DATABASE_URI`|`sqlite:///` + DATA_DIR + `blog.db`|数据库位置；可用环境变量 DATABASE_URL 覆盖|
|`check_same_thread=False`|连接参数|允许不同线程共用连接（Flask 多线程必需，否则报 `SQLite objects created in a thread can only be used in that same thread`）|
|`timeout=30`|连接参数|写锁等待上限（秒），防 `database is locked`|
|`pool_recycle=1800`|连接池参数|连接 30 分钟自动回收重建，防长连接假死|
|`pool_pre_ping=True`|连接池参数|每次取连接先 ping 一下，连接断了自动重连|

**为什么这些配置缺一不可？**① Flask 默认多线程处理请求，SQLite 默认「一个连接只能在一个线程用」，不关检查直接崩；② SQLite 写操作要拿锁，两个进程同时写会立刻报错，`timeout=30` 让第二个写者等 30 秒而不是立刻失败；③ 长连接闲置久了会被系统回收，`pool_recycle` 定期重建避免「连接已死但程序不知道」。

### 项目落地代码（真实源码，config.py 第 152 行）

```python

    'DATABASE_URL') or 'sqlite:///' + os.path.join(DATA_DIR, 'blog.db')
SQLALCHEMY_TRACK_MODIFICATIONS = False

    'pool_pre_ping': True,
    'pool_recycle': 1800,      # 连接 30 分钟自动回收
    'connect_args': {'check_same_thread': False, 'timeout': 30}
}
```

**`os.environ.get('DATABASE_URL') or 默认值`** 是「环境变量优先」的标准写法——想换数据库位置就在启动前设 `DATABASE_URL`，不设就用默认。

### 高频坑详解

- **模型加列查询报 `no such column`** → `create_all()` 不改旧表。**解法**：用 init_db 的 ALTER 补列（见 Flask\-SQLAlchemy 落地代码）。

- **db 文件损坏报 `file is not a database`** → 文件被写坏（断电、磁盘满、或复制了正在写入的文件）。**解法**：定期复制 blog.db 备份；复制前先关博客；用 DB Browser for SQLite 的「完整性检查」验证。

- **数据备份 = 复制一个文件** → 就这么简单。同步功能（云备份）本质也是把这个文件按块上传到 Gitee。

- **删除 blog.db 后文章全没了** → 正常现象，init_db 会重建空库 + 示例文章。**想找回**：从备份/云同步恢复。

- **`database is locked` 持续出现** → 有程序长期占着写锁。**排查**：关掉所有博客实例和 DB Browser；确认没有后台同步进程在写。

# 第三层 · 内容处理层（Markdown / Pygments / PyYAML / dateutil）

## python\-markdown：Markdown 转 HTML

### 角色定位

文章正文的加工核心：Markdown 原文 → HTML。带目录、代码高亮、表格等插件，结果缓存进 `rendered_html` 列避免重复渲染。**博客的「文章加工厂」——你写 `# 标题`、`**加粗**`、```` ```代码 ``` ````，它负责变成浏览器能显示的 `<h1>`、`<strong>`、`<pre>`。**

### 原理大白话

**为什么需要它？**浏览器不认识 Markdown——它只认 HTML。你在编辑器里写 `## 副标题`，浏览器要看到的是 `<h2>副标题</h2>`。python\-markdown 就是做这个转换的库：读入 Markdown 字符串，输出 HTML 字符串。

**插件（extensions）是什么？**Markdown 核心语法只有标题、列表、加粗等基础能力。插件在核心之上加功能：

- **FencedCodeExtension**：支持 ```` ```python ```` 这种「围栏代码块」（核心语法只有缩进 4 空格那种老式写法，很难用）。
- **tables**：支持 `| 列1 | 列2 |` 这种管道表格。
- **sane_lists**：列表嵌套更符合直觉。
- **nl2br**：普通换行转 `<br>`（否则 Markdown 里换行不生效，要空一行才是新段落）。
- **TocExtension**：自动给标题生成锚点 id + 目录（`permalink=True` 每个标题挂一个 ¶ 链接）。
- **codehilite**：代码块输出带高亮 class 的 HTML（配合 Pygments 的 CSS 才上色）。

**渲染结果为什么缓存？**一次 Markdown 渲染约几十毫秒，文章详情页每次访问都重渲染太浪费。项目把结果存进 `rendered_html` 列：写文章时自动渲染存入；编辑后清空；详情页读到空才渲染一次（懒回填）。

### 核心 API 详解

|API / 配置|用途|
|---|---|
|`markdown.Markdown(extensions=[...], extension_configs={...})`|创建渲染器，一次性配好插件（创建一次可反复 convert，别每次访问都 new）|
|`md.convert(text)`|渲染：Markdown 字符串 → HTML 字符串|
|`extension_configs={'codehilite': {'css_class': 'codehilite', ...}}`|给插件传配置：高亮 CSS 类名、是否行号、是否猜语言|
|`output_format='html5'`|输出 HTML5（默认已是，显式写更明确）|
|`TocExtension(permalink=True, toc_depth='2-4')`|目录插件：标题锚点 + 只给 2~4 级标题加|

### 项目落地代码（真实源码，app.py 第 613 行）

```python
def render_markdown(text):
    """Markdown -> HTML，带目录、代码高亮、表格等"""
    extensions = [
        FencedCodeExtension(),
        'tables',
        'sane_lists',
        TocExtension(permalink=True, toc_depth='2-4'),
        'codehilite',
        'nl2br',
    ]
    extension_configs = {
        'codehilite': {
            'css_class': 'codehilite',
            'linenums': False,
            'guess_lang': False,
        }
    }
    md = markdown.Markdown(
        extensions=extensions,
        extension_configs=extension_configs,
        output_format='html5'
    )
    return md.convert(text)
```

**逐行解释：**① `extensions` 列表一口气声明 6 个插件——这就是博客 Markdown 的全部能力边界；② `TocExtension(toc_depth='2-4')` 只给 2/3/4 级标题生成目录锚点（1 级标题是文章标题本身，不占目录）；③ `codehilite` 配 `css_class='codehilite'`——这个类名必须和 Pygments 生成 CSS 时用的前缀一致（下一节讲）；④ `md.convert(text)` 输出最终 HTML，存进 `rendered_html` 缓存列。

### 高频坑详解

- **代码块里还渲染 Markdown** → 没开 FencedCodeExtension，```` ``` ```` 围栏不被识别，内容被当普通段落继续解析。**解法**：`extensions` 必须含 `FencedCodeExtension()`。

- **换行消失** → 没开 nl2br，Markdown 里换行不生效（要空一行才分段）。**解法**：加 `'nl2br'` 到 extensions。

- **代码没颜色** → codehilite 只负责「贴高亮 class」，**上色靠 CSS**——而 CSS 是 Pygments 生成的（下一节）。两库必须配合。

- **每次访问都重渲染（慢）** → 没用缓存。**解法**：用 `rendered_html` 列 + 懒回填（详情页读到空才渲染，写文章时预渲染）。

- **用户写 `<script>` 被执行** → **XSS**。python\-markdown 默认不清理 HTML（它会原样输出用户写的 `<script>`）。**解法**：个人自用没问题；多人投稿需先过滤（用 bleach 库白名单清洗）再渲染。

## Pygments：代码高亮引擎

### 角色定位

给文章里的代码块「上色」：`HtmlFormatter(style='monokai').get_style_defs('.codehilite')` 生成高亮 CSS，挂到 `.codehilite` 类名下，正好匹配 codehilite 插件输出的代码块。**它是 python\-markdown 的「上色搭档」——一个负责贴 class，一个负责给 class 定义颜色。**

### 原理大白话

**代码高亮分两步，缺一不可：**

1. **标记（python\-markdown 的 codehilite 插件做）**：分析代码块属于什么语言（` ```python ` 声明），把每个 token 包上 `<span class="k">`、`<span class="s">` 这类 class——`k` 是关键字（keyword）、`s` 是字符串（string）、`c` 是注释（comment）等。
2. **上色（Pygments 做）**：生成一段 CSS，规定 `.codehilite .k { color: #f92672 }`（关键字紫色）、`.codehilite .s { color: #e6db74 }`（字符串黄色）……浏览器读到这段 CSS 就给代码上色了。

**为什么不用现成 CSS 文件？**Pygments 的 `HtmlFormatter(style='monokai')` 支持几十种配色主题（github/friendly/vim/monokai……），项目选 monokai（深色主题）。生成 CSS 是一次性操作（结果不会变），所以项目把它缓存成模块级常量——避免每次请求都重新生成（每次约 20ms）。

### 核心 API 详解

- **`HtmlFormatter(style='monokai')`**：选配色主题。`style` 可换：`'github'`（浅色）、`'friendly'`、`'vim'`、`'monokai'`（深色）等。

- **`.get_style_defs('.codehilite')`**：生成 CSS 字符串。参数是 CSS 前缀——**必须与 codehilite 插件的 `css_class` 完全一致**（项目两边都是 `'codehilite'`），否则类名对不上、不上色。

- **模块加载时生成一次即可**（约 20ms 开销，别放路由里）——项目在文件顶部生成 `_CODEHILITE_CSS` 常量。

- **模板输出时加 `|safe`**：CSS 字符串里有 `{`、`}`、`#` 等字符，Jinja2 自动转义会把 CSS 变源码。输出必须 `{{ codehilite_css | safe }}`。

### 项目落地代码（真实源码，app.py 第 43 行）

```python
from pygments.formatters import HtmlFormatter
# 【PP2 · 性能】HtmlFormatter 只实例化一次（pygments monokai 规则是纯常量），
#              避免每次 inject_globals 都做 20ms 量级的 CSS 规则扫描。
_CODEHILITE_CSS = HtmlFormatter(style='monokai').get_style_defs('.codehilite')
```

**为什么放模块顶部？**`HtmlFormatter(...)` 创建 + `get_style_defs(...)` 生成 CSS 是**纯计算**（同样的输入永远同样的输出）。放模块顶部只在启动时算一次，之后整个进程复用 `_CODEHILITE_CSS`。如果放路由里，每次请求都重算，白白浪费 20ms——这就是注释里说的 PP2 性能优化。

**模板里怎么用（base.html）：**

```html
<style>{{ codehilite_css | safe }}</style>
```

**`| safe` 为什么必须？**CSS 里的 `#f92672` 如果被 Jinja2 转义，`#` 会变成 `&#35;`，颜色值失效。

### 高频坑详解

- **CSS 类名对不上 → 不上色** → codehilite 插件 `css_class='codehilite'` 和 `get_style_defs('.codehilite')` 必须一致。**排查**：浏览器 F12 看代码块的 class 是什么，再看 CSS 选择器前缀。

- **CSS 显示成源码 → 没加 |safe** → 模板里 `<style>` 内容必须 `{{ codehilite_css | safe }}`。

- **高亮全一色 → 代码块没写语言标记** → ` ```python ` 没写或写错语言名，codehilite 无法识别（`guess_lang=False` 时不猜，按无语言处理）。**解法**：代码块必须带语言标记。

- **想换配色** → 改 `style='monokai'` 为其他值（如 `'github'`、`'friendly'`），重新打包即可。

详细手册：[Pygments · 博客项目实战手册](https://my.feishu.cn/docx/AwopdeNJ9o9y8VxtjGpcYlIhnVc)

## PyYAML：YAML 解析

### 角色定位

解析 Markdown 文件头部的 front\-matter（`---` 包裹的 YAML）和批量导入文件（uploads/sample_batch.yaml）。**它是「文件导入文章」功能的解析器——把 YAML 文本变成 Python 字典。**

### 原理大白话

**YAML 是什么？**一种「给人看的配置文件」格式，靠缩进表达层级：

```yaml
title: 我的第一篇博客
date: 2026-09-07
tags: [Python, 教程]
category: 技术
```

**front\-matter 是什么？**Markdown 文件最开头的 `---` 包裹区域，用来声明文章的元信息（标题、日期、标签）——不是正文的一部分。博客支持把带 front\-matter 的 `.md` 文件直接导入成文章。

**为什么用 `safe_load` 而不是 `load`？**`yaml.load()` 可以执行 YAML 里的 Python 对象标签（`!!python/object`），攻击者能借此执行任意代码——这就是著名的「YAML 反序列化漏洞」。`yaml.safe_load()` 只解析纯数据，拒绝对象标签，**安全**。项目所有解析都用 safe_load。

### 核心 API 详解

- **`yaml.safe_load(文本)`**：YAML 字符串 → Python 字典/列表。**必用 safe_load，永远不用 load**。

- **`yaml.YAMLError`**：解析失败统一异常（缩进错、冒号后没空格都会抛）。项目捕获后兜底：front\-matter 解析失败就当没有元信息，正文照常导入，不中断。

- **`parse_front_matter()`**：项目封装的函数——先用正则切出 `---` 之间的头部，再 safe_load，失败兜底返回 `({}, 全文)`。

### 项目落地代码（真实源码，app.py 第 674 行）

```python
def parse_front_matter(text):
    """解析 Markdown 头部 front-matter，返回 (meta_dict, body_text)"""
    if text.startswith('---'):
        match = re.match(r'^---\s*\n(.*?)\n---\s*\n?(.*)', text, flags=re.S)
        if match:
            try:
                meta = yaml.safe_load(match.group(1)) or {}
                body = match.group(2)
                return meta, body
            except yaml.YAMLError:
                pass
    return {}, text
```

**逐行解释：**① `re.match(r'^---\s*\n(.*?)\n---\s*\n?(.*)', text, flags=re.S)`——正则切三段：开头的 `---`、中间的 YAML 内容（非贪婪 `.*?`）、结尾的 `---` + 正文（`re.S` 让 `.` 匹配换行）；② `yaml.safe_load(...) or {}`——空内容解析返回 None，`or {}` 兜底成空字典；③ `except yaml.YAMLError: pass`——解析失败直接放弃元信息，正文照常返回，导入不中断。

### 高频坑详解

- **缩进错（Tab/冒号后没空格）→ ScannerError** → YAML 严格要求缩进：**不要用 Tab，统一空格**；冒号后面必须有空格（`title: xxx` 而不是 `title:xxx`）。

- **空内容解析返回 None → 取字段报错** → `yaml.safe_load('')` 返回 None。**解法**：`... or {}` 兜底再取字段。

- **中文乱码** → 文件必须 UTF\-8 编码，读取时 `open(path, encoding='utf-8')` 或 `.decode('utf-8')`。

- **标签字段拼错** → 导入后文章没标题/没日期。**排查**：对照 `uploads/sample_post.md` 的 front\-matter 格式照抄。

## python\-dateutil：智能日期解析

### 角色定位

导入文章时把各种格式的日期字符串（`2026-09-07`、`Sep 7, 2026`）转成标准时间对象存进 created_at。**它是「日期格式自由」的保障——用户怎么写日期，它都尽量认出来。**

### 原理大白话

**问题：**Python 标准库的 `datetime.strptime()` 解析日期必须给定格式：`'2026-09-07'` 要写 `'%Y-%m-%d'`，`'Sep 7, 2026'` 要写 `'%b %d, %Y'`——换一种写法就崩。**dateutil 的 `parser.parse()` 不需要格式**：它内部做了大量日期格式的智能匹配，绝大多数常见写法都能认出来。

**为什么只在导入时用？**正常发文章的日期是程序自己生成的（`datetime.datetime.utcnow()`），格式固定，不需要解析器。只有「导入别人的 Markdown 文件」时，文件里的 date 字段是用户手写的、格式不确定，才需要 dateutil 兜底。

### 核心 API 详解

- **`dateutil.parser.parse('2026-09-07')`**：智能识别常见日期写法，返回 datetime 对象。支持 `2026-09-07`、`Sep 7, 2026`、`2026/09/07`、`07-09-2026` 等大量格式。

- **项目写法**：`try: post.created_at = date_parser.parse(str(date_str)) except Exception: pass`——解析失败静默回退（不改日期，用默认值），不打断导入。

### 项目落地代码（真实源码，app.py 第 1773 行）

```python
# 处理指定日期
if date_str:
    try:
        from dateutil import parser as date_parser
        post.created_at = date_parser.parse(str(date_str))
    except Exception:
        pass
```

**为什么 try/except 全包住？**导入是批量操作，一个文件日期写错不该中断整批。解析失败就保持默认日期（当前时间），文件照样导入成功——「静默容错」是批量导入的正确姿势。

### 高频坑详解

- **纯数字串易误解析** → `parse('2026')` 可能被当成某个日期而不是年份。**解法**：先判断类型再 parse；导入代码里 `if date_str:` 确保空值不解析。

- **带时区字符串归档差 8 小时** → `parse('2026-09-07 12:00:00+08:00')` 返回带时区时间，转本地时区再存。**解法**：项目 v2.8.3 统一在模板显示层做时区转换（见 Jinja2 落地代码），入库统一存 UTC。

- **想「减一个月」用 timedelta 报错** → `timedelta` 不支持按月运算（`timedelta(days=30)` 是 30 天不是 1 个月）。**解法**：用 `dateutil.relativedelta.relativedelta(months=-1)`。

详细手册：[python\-dateutil · 博客项目实战手册](https://my.feishu.cn/docx/D9p8dpo2WouJktxe7q1c1vI7nwb)

## waitress：生产级 WSGI 服务器

### 角色定位

网页版生产模式（app.py run_server）和桌面版后台线程（main.py）的服务器。比 Flask 内置稳定、多线程、可配。**它是「博客真正跑起来的引擎」——Flask 负责业务逻辑，waitress 负责稳定地接收和返回请求。**

### 原理大白话

**为什么不用 Flask 自带的服务器？**Flask 内置的开发服务器（`app.run()`）为开发设计：单线程为主、有调试器、性能弱、不建议生产用。**waitress** 是纯 Python 写的生产级 WSGI 服务器：多线程并发、连接管理、超时控制都比内置服务器稳。**同一个 Flask 应用，开发时用内置服务器，生产/桌面版用 waitress——这正是 WSGI 标准带来的「换服务器不用改业务代码」。**

**两种启动方式的区别（关键）：**

- **`waitress.serve(app, ...)`**：**阻塞式**——调用后这个函数一直运行，后面代码永远不执行。适合「网页版」：脚本最后一行调它，程序就挂在这等请求。
- **`waitress.server.create_server(app, ...)` + `threading.Thread(server.run)`**：**非阻塞式**——create_server 只创建服务器对象不运行，把 `server.run` 丢进后台线程跑，主线程继续干别的（开窗口、挂托盘）。适合「桌面版」：窗口要显示，服务器要在后台跑，两个线程并行。

### 核心 API 详解

|API|用途|
|---|---|
|`waitress.serve(app, host=, port=, threads=8, ...)`|阻塞式启动（网页版放脚本末尾）；`threads` 并发线程数|
|`waitress.server.create_server(app, ...)`|非阻塞创建服务器对象（不运行）|
|`threading.Thread(target=server.run, daemon=True)`|把服务器跑进后台线程（桌面版窗口加载用）；`daemon=True` 主程序退出它跟着退出|
|`server.close()`|优雅关闭：停监听、等现有请求完成（托盘退出流程用）|
|`connection_limit`|最大并发连接数（防连接风暴）|
|`channel_timeout`|空闲连接超时（秒），超时断开防占用|

### 项目落地代码（真实源码）

**网页版（app.py 第 2516 行）：**

```python
try:
    from waitress import serve as waitress_serve
    waitress_serve(app, host=host, port=port,
                   threads=8,            # 并发线程数（个人博客足够）
                   connection_limit=512)
except ImportError:
    app.run(host=host, port=port, threaded=True)   # 未装 waitress 时退回
```

**`try/except ImportError` 回退**：没装 waitress 也能跑（退回 Flask 内置 + threaded 多线程）——这是依赖降级的优雅写法。

**桌面版（main.py）：**

```python
server = waitress.server.create_server(
    _app_mod.app, host='127.0.0.1', port=port,
    threads=8, channel_timeout=60, connection_limit=32)
t = threading.Thread(target=server.run, daemon=True)
t.start()
return t
```

**为什么桌面版用 create_server + 线程？**桌面版流程是「起服务 → 等就绪 → 开窗口 → 挂托盘」——如果直接用阻塞的 `serve()`，程序会永远卡在起服务那行，窗口永远弹不出来。必须非阻塞。

### 高频坑详解

- **serve() 阻塞 → 后面代码不执行** → 桌面版误用阻塞式 serve。**解法**：桌面版必须 `create_server` + `threading.Thread`。

- **端口占用 → 启动报错或白屏** → 之前有没退干净的进程。**解法**：`netstat -ano | findstr 端口` 找 PID，`taskkill /PID 数字 /F`；或 `BLOG_PORT` 换端口。

- **开发时想要热重载** → waitress 没有调试器和热重载。**解法**：开发用 `FLASK_DEBUG=1` + `python app.py`（内置服务器），发布/日常用 waitress。

- **日志里 `[博客服务] exited`** → waitress 线程异常退出。**排查**：看退出前最后几条日志，常见是端口被占或数据库文件损坏。

## pywebview：桌面窗口壳

### 角色定位

把博客网页装进 Windows 桌面窗口（WebView2 内核渲染），桌面版的「门面」。main.py 用它开 1280×820 窗口 + 配合托盘。**它是「桌面版」和「网页版」的唯一区别——同一个博客网页，浏览器里开是网页版，pywebview 窗口里开就是桌面版。**

### 原理大白话

**pywebview 是什么？**一个 Python 库：创建本地窗口，窗口里嵌一个系统浏览器内核（Windows 上默认用 WebView2，即 Chromium 内核）渲染你指定的 URL。**本质上它就是一个「没有地址栏、没有工具栏的迷你浏览器」**，而且这个窗口完全由 Python 控制（位置、大小、关闭行为、托盘联动）。

**为什么博客用 pywebview 而不是让用户开浏览器？**① 体验像「原生软件」：有自己的图标、托盘、窗口记忆；② 固定窗口尺寸和居中位置，界面整洁；③ 配合单实例锁、托盘，实现「关窗口程序还在后台跑」的桌面软件体验。

**v2.8.3 的窗口大小记忆**：`_build_create_window_kwargs` 先读 `window_state.json`（存在 data/ 目录），有记录就用上次调整的尺寸，没有才用默认 1280×820；`_bind_window_size_save` 监听窗口 `resized` 事件，**拖拽结束 0.8 秒后**（防抖）把最新大小写回文件——每次调整都会覆盖记忆，下次打开永远是你最近一次调好的大小；关闭窗口时还会强制 flush 一次，防止「刚调完就关」丢失记录。

### 核心 API 详解

|API|用途|
|---|---|
|`webview.create_window(标题, url, width=, height=, ...)`|创建窗口。`min_size=(w,h)` 最小尺寸；`background_color` 加载底色；`confirm_close` 关窗确认；`x/y` 窗口位置|
|`webview.start(gui='edgechromium')`|进入事件循环（**阻塞**）；指定 WebView2 后端|
|`window.show() / hide() / destroy() / restore()`|托盘交互核心：关窗转隐藏、点图标恢复、退出时销毁|
|`window.events.resized += 回调`|监听窗口尺寸变化（v2.8.3 窗口记忆的触发点）|

### 项目落地代码（真实源码，main.py）

```python
# v2.8.3：窗口大小记忆优先——读取 window_state.json，有记忆用记忆尺寸，无则 1280x820
cw_kwargs, _ = _build_create_window_kwargs('个人博客', f'http://127.0.0.1:{port}/')
window = webview.create_window(**cw_kwargs)   # 记忆尺寸（默认 1280x820），屏幕正中央
_bind_window_size_save(window)    # v2.8.3：拖拽调整大小后自动记住，下次启动沿用
_start_tray(window)               # 挂托盘
webview.start()                   # 进入窗口事件循环
```

**启动顺序为什么必须这样？**`webview.start()` 是**阻塞**的——调用后代码停在这行，直到窗口关闭才继续。所以「挂托盘」「绑定事件」这些准备工作必须放在 start **之前**；start 之后只剩退出清理逻辑。

### 高频坑详解

- **白屏** → 三选一：WebView2 Runtime 缺失（Win10/11 一般自带，装一下即可）；后台服务没起（看终端报错）；端口拼错（URL 与 waitress 实际端口不一致）。

- **start() 后的代码不执行** → start 是阻塞的。**解法**：所有窗口初始化、托盘绑定放 start 之前。

- **退出不干净（托盘图标残留/进程残留）** → 完整退出链：`window.destroy()` → `webview.start()` 返回 → `server.close()` → 释放互斥锁。缺一步都会留尾巴。

- **窗口大小记不住** → 旧版没有窗口记忆。**解法**：v2.8.3 已实现（见上）；如果手动调完没生效，确认用的是最新版且 data/ 目录可写。

详细手册：[pywebview · 博客项目实战手册](https://my.feishu.cn/docx/FQSCdBO5qoAQS7xwA5wcUFMQnpd)

# 第五层 · 前端层（Tailwind CSS / Vditor）

## Tailwind CSS：全站样式

### 角色定位

原子化 CSS 框架：在 HTML class 里堆工具类名（text-3xl、bg-cyan-500、rounded-[28px]）控制排版与配色。项目用 tailwind.min.js 运行时模式，零构建。**它是博客的「装修队」——所有页面的外观都靠 class 名堆出来。**

### 原理大白话

**传统 CSS 怎么写？**给元素起类名（`.card`、`.btn-primary`），再去 CSS 文件里定义 `.card { ... }` 的样式。项目大了 CSS 文件越来越长，类名越来越多，改样式要来回跳文件。

**Tailwind 的思路反过来：**不写自定义类名，直接用**原子工具类**——`text-3xl` 就是 `font-size: 1.875rem`，`bg-cyan-500` 就是 `background-color: #06b6d4`，`rounded-[28px]` 就是 `border-radius: 28px`。**你像搭积木一样在 HTML 里拼 class，基本不用写 CSS 文件。**好处：样式和结构在一起（改样式=改 HTML 里的 class），全站风格统一（都用同一套工具类）。

**运行时模式（项目用法）是什么？**Tailwind 通常要「构建」——扫描 HTML 生成 CSS 文件。项目用的是 tailwind.min.js **运行时版**：浏览器加载时动态扫描并生成样式，**零构建步骤**，改 class 刷新即生效。代价是首次加载稍慢，个人博客完全可接受。

### 核心用法详解

- **引入**：base.html 里 `<script src=".../tailwind.min.js"></script>` + `tailwind.config = { darkMode: 'class' }`（class 模式：html 标签有 `dark` class 就切深色主题）。

- **响应式前缀**：`sm:`/`md:`/`lg:`/`xl:` 按屏幕宽度生效——手机优先写基础样式，大屏用前缀覆盖：`class="text-sm md:text-lg"`（手机上小字，平板以上大字）。

- **任意值语法**：`rounded-[28px]`、`w-[calc(100%-2rem)]`——方括号里写任意 CSS 值，不用去 config 注册。

- **项目色板**：cyan/blue 主色 + purple/red 强调。新页面沿用同色系保持全站统一。

### 项目落地代码（真实源码，base.html）

```html
<html lang="zh-CN" class="{% if dark_mode %}dark{% endif %}">
<body class="bg-gray-50 dark:bg-gray-900 text-gray-900 dark:text-gray-100">
  <nav class="bg-white/80 backdrop-blur shadow-sm sticky top-0 z-50">
    ...
  </nav>
```

**读法：**`bg-white/80` = 白色 80% 透明；`backdrop-blur` = 背景模糊（毛玻璃）；`sticky top-0 z-50` = 吸顶导航（滚动时停在顶部）；`dark:bg-gray-900` = 深色模式下用深灰背景。**一个 class 一个效果，组合起来就是完整布局。**

### 高频坑详解

- **类名没效果** → 三选一：拼写错（`text-3xl` 不是 `text-3xl ` 多空格）；前缀顺序错（`hover:text-blue-600` 不是 `text-blue-600 hover:`）；任意值忘写方括号（`rounded-28px` 无效，必须 `rounded-[28px]`）。

- **深色模式不切换** → `darkMode` 没配 `'class'`（默认是 `'media'` 跟随系统）。**解法**：`tailwind.config = { darkMode: 'class' }`，且 html 标签要能增删 `dark` class。

- **运行时版 404 / 样式全没** → static/tailwind 目录缺失，或打包时没含 static。**解法**：确认 `static/tailwind/tailwind.min.js` 存在；打包 spec 的 SHARED_DATAS 必须含 static。

- **改样式不生效** → 浏览器缓存了旧 CSS/JS。**解法**：Ctrl\+F5 强刷。

详细手册：[Tailwind CSS · 博客项目实战手册](https://my.feishu.cn/docx/EBJWdqDsGoTOsOxkuvhcNcv5n5d)

## Vditor：Markdown 编辑器

### 角色定位

后台写文章页的编辑器：`templates/admin/post_form.html` 里 `new Vditor('vditor', {...})` 初始化，所见即所得，最后把 Markdown 原文提交后端。**它是博客的「文具」——你写文章时的打字界面。**

### 原理大白话

**为什么需要专门的编辑器？**写 Markdown 文章时，`<textarea>` 太简陋（看不到渲染效果），直接用 markdown-it 之类太重。**Vditor** 是一个国产 Markdown 编辑器：三种模式（所见即所得 wysiwyg / 分屏预览 / 源码）、工具栏（加粗、标题、代码、图片上传）、本地资源可部署（不依赖 CDN，打包版也能用）。

**关键机制：隐藏域提交。**Vditor 渲染的内容在它自己的内部区域，**不在表单里**。提交表单时浏览器只会提交表单内元素——所以必须在提交前把 Vditor 的 Markdown 原文写进一个隐藏的 `<input>`，后端从隐藏域取值。**忘了这步，保存后后端收到空内容。**

### 核心 API 详解

|API / 配置|用途|
|---|---|
|`new Vditor('元素id', {...})`|初始化编辑器。`cdn: '/static/vditor'` 本地资源（打包版不依赖外网）；`lang: 'zh_CN'` 中文；`mode: 'wysiwyg'` 所见即所得|
|`vditor.getValue()`|取 Markdown 原文（提交前塞进隐藏域用）|
|`vditor.setValue(文本)`|设置内容（编辑文章时回填初始内容）|
|`after: () => {...}`|初始化完成回调（编辑模式在这里 setValue）|
|`cache: { enable: false }`|关掉浏览器草稿缓存（防旧内容串台）|
|`upload: { url, fieldName }`|图片上传配置（可接后端上传接口）|

### 项目落地代码（真实源码，post_form.html 简化）

```javascript
const vditor = new Vditor('vditor', {
    cdn: '/static/vditor',
    lang: 'zh_CN',
    mode: 'wysiwyg',
    cache: { enable: false },
    after: function () {
        vditor.setValue(initialContent);   // 编辑时回填
    }
});

// 提交前：把 Markdown 原文写进隐藏域
document.getElementById('post-form').addEventListener('submit', function () {
    document.getElementById('content-hidden').value = vditor.getValue();
});
```

**后端接收：**`content = request.form.get('content')`——content 就是隐藏域 `content-hidden` 的值，即 Markdown 原文。

### 高频坑详解

- **编辑器空白** → index.min.js 404 或引入顺序错。**解法**：先引 CSS 后引 JS；确认 `static/vditor/` 目录完整；打包版确认 SHARED_DATAS 含 static。

- **保存后后端收空 content** → 隐藏域没赋值或 JS 没绑定 submit。**解法**：核对隐藏域 `name="content"` 和 `vditor.getValue()` 赋值代码；F12 看提交的 Form Data。

- **编辑文章没回填** → 没在 `after` 回调里 `setValue`。**解法**：编辑模式在 after 里 setValue(初始内容)；注意 setValue 要在 Vditor 初始化完成后调用。

- **预览和发布样式不一致** → 编辑器预览是 Vditor 自己渲染的，发布后是后端 python\-markdown 渲染的，两者实现不同。**解法**：以发布效果为准；可在后台做 /api/preview 联调。

详细手册：[Vditor · 博客项目实战手册](https://my.feishu.cn/docx/NGlAd3E3koVLmvxrDYacYM9Bn3d)

# 第六层 · 打包层（PyInstaller）

## PyInstaller：绿色版打包

### 角色定位

把项目打包成「个人博客绿色版」：exe + 配套文件文件夹（onedir），目标机无需装 Python。配置在 `blog_desktop.spec`。**它是博客的「出厂包装」——把一个 Python 项目变成普通人双击就能用的软件。**

### 原理大白话

**PyInstaller 做什么？**Python 程序要跑必须有 Python 解释器 + 依赖库。目标用户电脑上不一定有。PyInstaller 把**解释器 + 你的代码 + 所有依赖库**打包在一起：onedir 模式生成一个文件夹，里面 `个人博客.exe` 双击就运行，目标机零安装。

**打包后的资源目录（重要概念）：**打包后，你的 templates/static 等**只读资源**被打进 `_internal` 目录，Python 代码里 `os.path.join('templates')` 这种相对路径会失效——必须用 `sys._MEIPASS`（PyInstaller 提供的打包资源根目录）。项目用 `Config.RESOURCE_DIR` 封装了这一点：源码运行时指向项目目录，打包后指向 `_internal`。

**数据目录为什么不能打进去？**blog.db（你的文章数据）、uploads（图片）、window_state.json（窗口记忆）是**用户数据**，必须留在打包文件夹外面（DATA_DIR）——否则升级版本时用户数据全丢。**这就是「纯净版」的原理：打包时不带 blog.db，用户拿到的是全新博客。**

### 核心配置详解

|配置|用途|
|---|---|
|`SHARED_DATAS`|把 templates/static/uploads 等只读资源打进包（\_internal）；**漏了打包后找不到模板**|
|`EXCLUDES`|排除 numpy/tkinter 等无关库，瘦身|
|`HIDDEN_IMPORTS`|补动态加载模块：webview.platforms.*、waitress、pythonnet、clr_loader、gitee_backup 等（**漏了必崩**）|
|`EXE(..., console=False, icon=logo.ico)`|无控制台黑窗 + exe 图标|
|`COLLECT 钩子`|把 logo.ico 外置到 exe 同级，用户可自行替换图标|

**为什么有 HIDDEN_IMPORTS？**PyInstaller 靠「静态分析」找依赖——但有些模块是**运行时动态导入**的（`importlib` 或字符串名字导入），静态分析看不到。webview 的平台模块、gitee_backup 等必须在 HIDDEN_IMPORTS 里显式声明，否则运行时报 `ModuleNotFoundError`。

### 高频坑详解

- **打包后找不到模板/静态文件** → SHARED_DATAS 缺 templates/static，或代码用相对路径。**解法**：spec 的 SHARED_DATAS 补全；代码必须用 `Config.RESOURCE_DIR`。

- **打包后 ModuleNotFoundError** → 动态导入模块没进 HIDDEN_IMPORTS。**解法**：报错说缺哪个，就把哪个加进 HIDDEN_IMPORTS 重新打包。

- **双击 exe 没反应** → 命令行跑 exe 看报错（会显示在终端）；或临时 `console=True` 打包排查。

- **中文路径打包失败** → 部分库不支持中文路径。**解法**：项目放英文路径（`D:\blog`），打包命令也在英文路径下执行。

- **改了代码还是旧行为** → PyInstaller 缓存了旧构建。**解法**：先删 `build/` 和 `dist/` 再打包。

- **打包把个人数据带进去了** → 打包前必须删 blog.db 等数据文件（纯净版）。**解法**：按「打包清单」检查 data/ 目录，只保留必须的资源文件。

详细手册：[PyInstaller · 博客项目打包手册](https://my.feishu.cn/docx/QO4edvLxmo98POxKcYlcqdCunTe)
